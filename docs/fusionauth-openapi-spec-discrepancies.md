# FusionAuth OpenAPI specification discrepancies

This document lists places where the FusionAuth OpenAPI specification (`openapi.yaml`, API version **1.67.0**) does not match the behavior of the live FusionAuth API. It is written so it can be filed as an upstream bug report against FusionAuth. Each finding notes whether we have already worked around it in our generated client.

## Summary

The spec has four recurring classes of inaccuracy: (1) JSON objects keyed by a parent id are declared as arrays (`Map<UUID, List<X>>` modeled as `array`); (2) identifier parameters that carry UUIDs omit `format: uuid` (or use a non-standard uppercase `format: UUID`); (3) `GET` search and "retrieve all" variants are missing for endpoints that only model `POST`/`create`; (4) the OAuth 2.0 form-encoded endpoints (`/oauth2/token`, `/oauth2/introspect`, device endpoints) declare no request body at all. There are also several individual type/parameter errors.

## How this was determined

Every FusionAuth API documentation page under `https://fusionauth.io/docs/apis/` was read and compared, endpoint by endpoint, against the operations and schemas in `openapi.yaml`. Ambiguous cases were verified against a running FusionAuth instance by observing real request/response shapes (e.g. JSON deserialization error chains reveal the true container type; passing a non-UUID to a UUID path param returns a `400` conversion error vs a `404` not-found). The spec under review is 1.67.0; live verification was performed against a running **1.67.1** instance.

## Legend

- **Status** — `Fixed`: already corrected in our local copy of the spec / client. `Open`: still incorrect upstream and in our copy. `N/A`: investigated and found not to be a bug (withdrawn).
- **Confidence** — for open items: `High` (verified against the live API), `Medium` (documented but not live-verified, or version-skew), `Low` (cosmetic / arguably intentional).

## High-impact items, in detail

### Maps modeled as arrays (#1, #6, #7, #8)

This is the most common and most damaging pattern. FusionAuth serializes several collections as a JSON object keyed by a parent entity id, but the spec declares them as plain arrays, so a generated client deserializes them incorrectly.

- `Errors.fieldErrors` — keyed by field path, e.g. `{"application.name": [{"code": "..."}]}` — should be `Map<String, List<Error>>`.
- `Group.roles` — keyed by applicationId, e.g. `{"<applicationId>": [{ApplicationRole}]}` — should be `Map<UUID, List<ApplicationRole>>`.
- `MemberRequest.members` / `MemberResponse.members` — keyed by groupId, e.g. `{"<groupId>": [{GroupMember}]}` — should be `Map<UUID, List<GroupMember>>`.
- `MemberDeleteRequest.members` — keyed by groupId, value is a list of user-id UUIDs — should be `Map<UUID, List<UUID>>`.

In each case the correct OpenAPI shape is `type: object` with `additionalProperties` referencing the element (or `array` of element).

### OAuth 2.0 endpoints declare no request body (#9)

`POST /oauth2/token`, `POST /oauth2/introspect`, and the device endpoints accept `application/x-www-form-urlencoded` form fields, but in the spec these operations have `parameters: []` and no `requestBody`. A generated client therefore sends an empty body and cannot complete a token exchange. The relevant request schemas already exist in `components.schemas` but are never referenced from any operation, and the string `x-www-form-urlencoded` does not appear anywhere in the document.

### `GET /api/jwt/public-key` uses `kid`, not `keyId` (#10)

The query parameter is `kid` (the JWK key id, an opaque string), not `keyId`, and it is not a UUID. Verified live: `?kid=<value>` returns a single-key `PublicKeyResponse`, while `?keyId=<value>` is silently ignored and the server returns the "all public keys" response.

### Missing `GET` variants (#13, #14)

FusionAuth search endpoints support both `GET` (criteria as query params) and `POST` (criteria in the body), but the spec models only `POST`. Separately, the `messenger`, `connector`, `theme`, `form`, and `form/field` resources have a documented `GET` "retrieve all" that the spec omits entirely (only `POST`/create is present).

## Confirmed correct — please do not "fix" these

During the audit these looked suspicious but were verified to be correct as written, and should be left as plain strings / as-is:

- `pendingLinkId`, `connectionTestId`, and `identityProviderUserId` are **opaque strings, not UUIDs**. The connection-test docs state `connectionTestId` "is a String, not a UUID"; a non-UUID `pendingLinkId` returns `404` (not a `400` UUID-conversion error). `identityProviderUserId` is a third-party identifier.
- `twoFactorId`, `twoFactorTrustId`, `methodId`, and `code` are opaque strings, not UUIDs.
- `GET /api/webauthn/{id}` — the `{id}` path param **is** a UUID (the FusionAuth credential record id), distinct from the base64url `credentialId` / `rawId` fields that appear in WebAuthn request bodies.
- `keyId` (both crypto keys at `/api/key/{keyId}` and API keys at `/api/api-key/{keyId}`) and the refresh `tokenId` **are** UUIDs.

## Environment

- Specification: FusionAuth OpenAPI `openapi.yaml`, `info.version: 1.67.0`.
- Live verification: performed against a running **1.67.1** instance.
- Items 1–23, 25, 26, and 27 have been corrected in our local copy of the spec (`features/fix-openapi`). All of them remain open **upstream** — that is what this report is for.
- Item 24 was withdrawn — `logoutURL` is a documented top-level field of the OAuth configuration response, so the spec is correct; it is simply omitted from responses when null.
- Note (extends #27): the content-less `default` error response was **not** unique to the two application GETs — 41 operations total had it. All 41 were given the `Errors` content schema, so every operation's `default` response now references `#/components/schemas/Errors`.
- Item 26 (`GET /api/system/reindex`) is a real endpoint: it returns `202` while a reindex is in progress and `404` when none is running (the `404` is the "no reindex running" status, not a missing route). A `GET` operation (`retrieveReindexStatus`) with those response codes was added.
